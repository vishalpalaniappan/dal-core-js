# Implementation Module Planning

This engine has two modules:
- The design module is used to build the design and automatically debug its behavior
- The implementation module is used to implement the design and map the designs behavior onto the implementation

![Realization Loop](/src/docs/loop.JPG)        

The structure of the design is projected onto the implementation. As such, the interaction between the two modules moves in one direction. Then through the instrumentation, execution and transformation, the information moves back in the other direction, completing the loop.

It can also be noted that the implementation must be able to generate the instrumentation and the design must be able interpret the execution through the behavior. However, it is clear that the mapping is already doing the transfom and it is fair to call that process the Semantic Transform. The instrumentation and transformation are just a result of the information that the mapping makes avaialble.

Note: Practically, I am doing the instrumentation in python because I like the AST library. However, it is clear that the implementation module of this engine has the necessary information to instrument the source. A javascript python parser could easily implement the instrumentation logic. There is a discussion to be had about where the actual instrumentation tools will live.

It can also be seen that the environment is an impulse into this loop that causes the design and corresponding implementation to evolve. In this sense, failures are inputs into this loop, they are the stimulus the environment provides to feed this loop. For a given environment, failures reveal the missing information that the design needs to learn to converge on an ideal model within the scope of its knowledge. As the environment changes, the feedback loop iterates and the design reconverges.

## Design Module
At a high level:
- Each design is made up of a collection of graphs. 
- Each graph is made up of nodes. 
- Each node exhibits a behavior and has participants. 
- Each participant has invariants. 
- These invariants define the correctness of the behavior.

## Implementation Module
The implementation module contains the source files that realize the design. Each source file is parsed into an index of statements and the designs behavior and participants are projected onto the implementations statements and variables. As a result, each statement in the implementation can correspond to a behavior in the design and each variable in the statement can correspond to a participant in that behavior. 

As such the class structure will have to reflect this hierarchy:

- Implementation Class 
- File Class (version management happens here)
- Source Class (versioning happens here)
- Map Class

The Implementaiton class is the root of this module, it contains all the files in the implementation.
The File class is made up of a collection of source versions.
The source class is made up of its content and the statement index generated by parsing its content.
The statement index class is made up of a collection of map objects which defines the mapping.
The Map class contains a projection of the behaviors and participants from the design onto it.


## Details
I will identify the attributes of the classes from the leaf to the root. 

### Map Class
- Behavior ID
- Participants and Variables
- Line Numbers
- UID

This class contains a behavior ID, a list of (participant, variable) pairs and the line number of the statement it is mapping in the program. This class also has a UID. 

### Source Class
- Content
- Statement Index (collection of maps)
- Version ID
- Timestamp

This class establishes the version of the source (which is made up of the statement index and its content). This class will become an input into the versioning system. Meaning, it will provide versions of the statement index and source that will be diffed to preserve the semantic identity of the statements as described by the UIDs. This means that the versioning system will projec the UID's forward and overwrite what was assigned by the parser. 

### File Class
- List of source versions

This class contains a list of source versions and it will implement the versioning logic. 

### Implementation Class
- List of files

Tis class contains a list of files and it will produce the output that will be accepted by the instrumenter.
